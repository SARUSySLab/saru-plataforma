## Track 1, Gap físico (PRIORIDADE #1: load sensitivity)

### Diagnóstico confirmado por medição
- Caminho **escalar-μ** (`qss_solver.py` L424-434 fwd, L501-507 bwd) usa `mu` constante. Este é o caminho do **oráculo calibrado** (teste `test_qss_calibration.py` roda com `use_pacejka=False`).
- Medição direta da calibração canônica (992 GT3 R @ Interlagos bundled): `lap=94.23s · **peak_lat=3.77g** · peak_accel=1.29g · peak_brake=-2.04g · vmax=267 km/h`.
- 3.77g lateral é **pior** que os 2.4-2.8g do `PHYSICS_AUDIT.md`. Causa: `a_lat_max = μ·g·(1 + F_df/(m·g))` cresce sem teto com downforce; μ=1.80 foi inflado p/ acertar o lap **compensando** a ausência de load sensitivity → lap certo, física errada.
- Caminho **Pacejka** (`use_pacejka=True`, L407-421) também NÃO tem load sensitivity: `_tire_grip_caps` amostra a MF com `D=1` → recupera `μ·Fz` **linear** em Fz. Nenhum dos dois caminhos tem o efeito.

### Fórmula de referência (lts-hase, validada)
`partnerships/lts-hase/src/simulation/lap_time_solver.py:452-456,508-517`:
```python
_K_LS = 0.20                                    # grip loss por fração de Fz
_Fz_static    = p.m * g / 2.0                   # carga estática por eixo [N]
_tw           = max(p.track_width, 0.5)
_arb_frac_max = max(p.k_roll_front, p.k_roll_rear) / _k_roll_total
delta_fz_frac = np.clip(m*a_lat*h_cg*_arb_frac_max/(_tw*_Fz_static), 0.0, 0.95)
mu_eff        = mu * (1.0 - _K_LS * delta_fz_frac)
```

### Onde plugar (`qss_solver.py`)
1. **Fwd scalar** L425-426: `mu_lat`/`mu_lon` → `mu_eff_lat`/`mu_eff_lon` via `delta_fz_frac(a_lat_cur)`.
2. **Bwd scalar** L502: `mu_lon_bw` → idem com `a_lat_next`.
3. (Opcional, fase 2) caminho Pacejka: load sensitivity real via `LFZO`/`pDy2` da MF6.2 em vez do multiplicador empírico.

### Bloqueio de portabilidade (resolver antes do TDD)
- `_LegacyVehicleParams` tem `h_cg` ✔ mas **falta** `track_width` e `k_roll_front/rear`.
- `to_solver_dict()` (`parameters.py:254`) exporta `h_cg` ✔, **não** exporta `track_width` nem `k_roll`.
- **`k_roll_front/rear` NÃO EXISTE** em `parameters.py` (só citado em docstring). `track_width` e `cg_height` existem em `mass_geometry`.
- → Duas opções:
  - **A (mínima, recomendada V1):** load sensitivity sem split de ARB: `delta_fz_frac = clip(a_lat·h_cg/(g·tw), 0, 0.95)`. Só precisa de `h_cg`+`track_width` (ambos já existem). Adicionar `track_width` ao `to_solver_dict` + `_LegacyVehicleParams`.
  - **B (fiel ao legado):** adicionar campos `k_roll_front/rear` ao `SuspensionParams`/`to_solver_dict`. Mais trabalho, refinamento de balanço por eixo. V2.

### Guardrail, tensão crítica (LER antes de implementar)
O caminho escalar **É** o oráculo 94.0s. Ligar load sensitivity nele **derruba grip de curva → lap sobe → regride**. Logo:
1. **Fase 1 (sem OK de calibração):** flag opt-in `use_load_sensitivity` **default `False`**. Default off = baseline byte-idêntico (94.23s preservado). TDD: (a) flag off ⇒ lap idêntico ao atual; (b) flag on ⇒ `peak_lat_g ≤ ~2.0` p/ 992.
2. **Fase 2 (requer OK explícito do Vitor):** flipar default + **re-calibrar μ p/ cima** p/ recuperar 94.0s com peak lat realista. Isto é exatamente a ordem que `calibration-guardrails.md` exige ("load sensitivity é pré-requisito da calibração definitiva de pneus"). Mudança ≥0.5s ⇒ aprovação antes do commit.

A 94.0s do oráculo usa **μ=1.80 inflado** p/ mascarar load-sensitivity ausente → peak lat **3.77 g**
(irreal). Num 14-DOF que JÁ tem **transferência de carga + per-wheel Fz + load-sens via MF**, copiar
μ=1.80 = **dupla contagem de grip** → erro grosseiro. **Porte os ALVOS, não os params:**
- alvo lap: 992 GT3 R @ Interlagos **94.0-94.4 s** (WEC); McLaren 720S @ Barcelona 103.5-105 s.
- μ honesto de slick GT3 ≈ **1.4-1.5** (não 1.8). Re-derive params no 14-DOF e re-valide ao alvo.

### Contrato de oráculo (ADR-010, não re-decidir)

core; é alvo hi-fi validado contra ele. Contrato de fio: **vehicle YAML + track HDF5 → lap_time**.
Interchange só CSV/JSON/HDF5, nunca `.mat`/pickle.

### Garimpe os órfãos, física já existe, não reinvente

### Onde o QSS NÃO ajuda (foco da pesquisa do AG)
O 14-DOF ganha de graça o que o QSS não tem (load transfer, roll, per-wheel). Pesquise o que o
oráculo QSS **não consegue validar**:
- **Pneu transiente** (relaxation length σ), QSS é quase-estático, zero dinâmica de pneu.
- **MF6.2 completa**, `.tir` reais em `~/Projects/_shared/tire_data/` (Pirelli Scorpion, 357 coef).
  QSS só usa MF simplificada D=1.
- **K&C real** (camber gain, RC, bump steer), do C++ ou hardpoints.
- **Damper/ARB não-linear, anti-geometria**, ausentes no QSS.
